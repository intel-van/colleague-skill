# dot-skill 深度架构分析与经验沉淀

> 分析时间：2026-06-11
> 分析目标：拆解 dot-skill (colleague-skill) 的架构设计决策，提炼可迁移到其他项目中的模式和经验

---

## 一、这个项目在做什么

**dot-skill**（原名 colleague.skill）是一个**人物蒸馏引擎**。它做的事情是：把一个人的思维方式、表达风格、决策模式、工作方法，从原材料（聊天记录、文档、音视频）中提取出来，打包成一个可复用的 AI Skill。

### 核心能力

| 能力 | 说明 |
|------|------|
| **三类人物** | colleague（同事）、relationship（亲密关系）、celebrity（名人/公众人物） |
| **双线架构** | Persona（性格表达层）+ Work（能力执行层），可独立或组合使用 |
| **自动采集** | 对接飞书、钉钉、Slack、微信聊天记录、邮件等 |
| **名人研究** | 6 维度系统研究（著作、对话、表达DNA、决策、他者视角、时间线） |
| **持续进化** | 追加文件自动合并、对话纠正实时更新，版本自动存档 |
| **量产输出** | 一次蒸馏生成 SKILL.md / work.md / persona.md / 各宿主安装脚本 |

### 工作流程

```
用户触发 /dot-skill
   ↓
Step 0: 选择人物类型 (colleague / relationship / celebrity)
   ↓
Step 1: 基础信息录入 (花名/公司/性格标签等，可跳过)
   ↓
Step 2: 原材料导入 (飞书/钉钉/文件/粘贴/跳过)
   ↓
Step 3: 分析 (并行执行)
   ├── 线路A: Work Skill 分析 ← work_analyzer.md
   └── 线路B: Persona 分析 ← persona_analyzer.md (Family-specific)
   ↓
Step 4: 预览确认
   ↓
Step 5: skill_writer.py 写入文件 → 立即可用
   ↓
[持续进化]: 追加文件/对话纠正 → merger/correction_handler → 版本管理
```

## 二、架构深度拆解

### 2.1 三层 Prompt 管线

```
        intake  (采集信息)
           │
           ▼
  ┌────────────────┐
  │  analyzer      │  ← 从原材料提取特征
  │  (work/persona)│
  └────────┬───────┘
           ▼
  ┌────────────────┐
  │  builder       │  ← 按模板填充生成
  │  (work/persona)│
  └───────┬────────┘
           │
           ▼
  ┌────────────────┐
  │  merger        │  ← 将来增量合并
  └────────────────┘
```

**关键设计点**：analyzer 和 builder 是分离的。analyzer 只做"从原材料中提取特征"，builder 只做"按固定模板填充"。这种分离让特征提取逻辑和输出格式逻辑可以独立迭代。

### 2.2 Colleague 的 6 层 Persona 架构

```
Layer 0: 硬覆盖层        ← 手动标签直接翻译，最高优先级
Layer 1: 身份层          ← 公司/职级/性别/MBTI
Layer 2: 表达风格层      ← 口头禅/句长/emoji/正式程度
Layer 3: 决策与判断层    ← 优先级/推进/回避/拒绝方式
Layer 4: 人际行为层      ← 对上级/下级/平级/压力下
Layer 5: 边界与雷区      ← 抵触/拒绝/回避
Layer 6: Correction 层   ← 对话纠正追加，滚动更新
```

**精华**：每一层都有明确的优先级。Layer 0 最高，意味着用户手动打的标签可以覆盖文件分析得出的结论。Correction 层是运行时纠错机制，让用户可以在使用过程中持续校准。

### 2.3 Celebrity 的 8 层架构 + Agentic Protocol

比 colleague 多了：

- **Mental Models**（心智模型）：三重门筛选（跨上下文复现、生成力、排他性）
- **Decision Heuristics**（决策启发式）：if-then 规则
- **Anti-patterns & Honest Boundaries**（反模式与诚实边界）：知道不知道什么
- **Contradictions**（矛盾）：保留矛盾，不强制一致
- **Intellectual Genealogy**（智识谱系）：受谁影响、与谁决裂、影响谁
- **Agentic Protocol**：面对新问题时，按该人物的方式去研究再回答，而非仅凭记忆

### 2.4 Research 管线（celebrity）

```
                  ┌─────────────────────────────┐
                  │  6 维度并行采集               │
                  │  著作 · 对话 · 表达DNA        │
                  │  决策 · 他者视角 · 时间线     │
                  └─────────────┬───────────────┘
                                │
                                ▼
                  质量关卡 (Phase 1.5)
                  展示维度覆盖表 → 用户确认
                                │
              ┌─────────────────┼────────────────┐
              ▼                 ▼                 ▼
   budget-friendly        budget-unfriendly
   3 track files          6 track files
   ├─ merge_research.py   ├─ audit (PASS/FAIL)
                          ├─ synthesis (triple-gate)
                          └─ validation (known-answer check)
```

预算友好版与预算不友好版的核心区别：

| 维度 | budget-friendly | budget-unfriendly |
|------|----------------|-------------------|
| 文件数 | 3 个（合并维度） | 6 个（独立维度） |
| 信源门槛 | URL ≥ 2, 文件 ≥ 3 | URL ≥ 8, 文件 ≥ 6 |
| 步骤 | 采集 → 展示确认 → 分析 | 采集 → audit → synthesis → validation |
| 每条证据 | 无权重要求 | source weight 1-7 标注 |
| 冷门检测 | 来源 < 10 | 同上 |

### 2.5 关键设计原则

**品味原则（Taste Principles）**：

1. 长文 > 金句
2. 争议 > 共识
3. 变化 > 固定
4. 一手 > 二手
5. 手艺讨论 > 生平八卦
6. 重复模式 > 一次性爆论

**信源黑名单**：知乎、微信公众号、百度百科、内容农场、AI 生成页面——永远不引用。

**标签翻译规则**：不写形容词，写具体行为。例如不写"你很强势"，而是写"被人质疑方案时，你不解释，而是反问'你的判断依据是什么'"。

**诚实架构（Honest Architecture）**：

- 每个维度不足时标注"原材料不足"
- 冷门人物自动限制心智模型数量（2-3 个）
- 矛盾不抹平，保留为特征
- 不编造 URL、引用、书名来通过质量检查

## 三、可以吸取的经验

### 3.1 Prompt 工程方面

**① Analyzer/Builder 分离**

绝大多数 prompt 项目把"分析"和"生成"放在一个 prompt 里。这里拆分后，analyzer 只输出结构化数据，builder 只做模板填充。好处是：

- 可以换 builder 模板不改分析逻辑
- analyzer 输出的结构化数据可以被 merger 直接复用
- 更容易做多语言（中英文各一套 builder 但共享 analyzer）

**② Persona 分层架构**

6-8 层结构设计非常精密：

- 最顶层（Layer 0）是硬覆盖规则，优先级最高
- 最底层（Correction）是运行时反馈，滚动积累
- 中间层按"表达→决策→人际"划分，每层有明确的提取来源和填充模板
- 这种分层让"追加文件"和"对话纠正"可以精确定位到某一层，不波及全量

**③ 质量关卡嵌入流程**

不是最后才检查，而是在流程的多个节点插入质量门：

- Phase 1.5（采集后）：展示维度覆盖矩阵，用户确认
- Phase 2.5（提炼后）：展示候选心智模型与三重门结果
- 最终：quality_check.py 自动化检查

**④ 诚实设计**

- 不编造来源
- 标注冷门人物
- 明确告知局限性
- "基于有限信息"标记

### 3.2 架构设计方面

**⑤ 多 family 共享核心 + 差异化扩展**

三个 family 共享相同的管线结构（intake → analyzer → builder → merger），但每个 family 有自己的 prompt 实现。核心的 work_analyzer 和 work_builder 是公用的，celebrity 场景下对 work 语义做了重定义（偏方法论/判断框架而非工作职责）。

**⑥ 统一的写入层**

所有生成/更新操作不直接写文件，而是通过 skill_writer.py：

- 先写临时文件（`/tmp/dot_skill_{slug}_*.md`）
- 再调 writer 统一生成所有产物（SKILL.md / work.md / persona.md / manifest.json / meta.json）
- 安装到宿主也通过 writer（`--install-claude-skill` 等）

这相当于一个"事务性写入层"——保证生成的原子性和一致性。

**⑦ 版本管理即基础设施**

version_manager.py 在每次更新前自动备份当前版本。这不只是"好习惯"，而是建立用户信任的关键：用户敢不断调优，因为知道可以回滚。

**⑧ 工具链的灵活性原则**

SKILL.md 中多次强调：如果采集脚本跑不通，就直接写 Python 调 API。不把用户锁死在工具上，把工具视为"默认实现"而非"唯一路径"。

### 3.3 产品/体验方面

**⑨ 全跳过设计**

3 个基础问题（花名/基本信息/性格画像）中，除花名外均可跳过。原材料导入可以不提供。这意味着**哪怕只给一句话，也能生成一个 Skill**。这极大降低了使用门槛。

**⑩ 渐进式深度**

celebrity 默认走 budget-friendly（快），用户可以选择 budget-unfriendly（深但不快）——但需要用户主动要求。这避免了"一上来就吓退用户"的问题。

**⑪ 纠正在对话中进行**

用户不需要知道文件结构、不需要写 patch。说一句"这不对，他不会这样"，correction_handler 自动识别意图、判断归属、生成 patch、调用 writer 更新。这是真正的"对话式运维"。

**⑫ 多宿主兼容**

一套 prompt 系统适配 Claude Code / Hermes / OpenClaw / Codex 四个宿主。关键策略：

- 只依赖 Read / Write / Edit / Bash 四个基础工具
- 不假设任意宿主的特殊能力
- 路径问题靠环境变量而非硬编码

### 3.4 具体技术细节可复用

**⑬ 职级对照表**

intake.md 里内置了字节/阿里/腾讯/百度/美团等公司的职级对照表。这在做 colleague 类场景时极为实用——用户说"字节 2-1"你就能自动映射。

**⑭ 标签翻译库**

persona_analyzer.md 里把每个标签都翻译成了具体的行为规则。例如"甩锅高手"→"遇到问题第一反应是找外部原因；被问责时先说'当时需求没说清楚'"。这个思想可以复用：任何标签系统都应该有对应的行为描述库。

**⑮ 三重门筛选心智模型**

celebrity 的心智模型候选必须通过三重门：

1. 跨上下文复现（至少在不同领域出现 2 次）
2. 生成力（能预测对新问题的判断，不只是复述历史观点）
3. 排他性（有辨别力，不是通用智慧）

这是一个非常高质量的筛选机制。

**⑯ Known-answer check**

budget-unfriendly 的 validation 阶段要做已知答案检查：拿人物确实说过/做过的事情来测试生成的 Skill，看它的回答是否与真实情况一致。这是蒸馏质量的终极校验。

## 五、总结

这个项目不是"做个 AI 聊天角色"，而是**一个高度工程化的认知蒸馏系统**——从信息采集、特征提取、模板生成到持续纠错，每个环节都有精心设计的 prompt 和工具支持。它的核心创新在于**把"一个人"抽象为多层结构化描述（表达层 × 决策层 × 知识层），让 AI 不再是模仿口吻，而是真正用那个人的框架去思考**。

最有价值的可迁移设计模式：

1. **Analyzer/Builder 分离** — 分析逻辑与生成逻辑解耦
2. **分层 Persona 架构** — 优先级驱动的多层描述
3. **质量关卡嵌入流程** — 不在最后才检验质量
4. **诚实架构** — 知道不知道什么，比知道什么更重要
5. **全跳过设计** — 降低使用门槛，让用户"先进来"
6. **对话式纠错** — 运行时校准，无需理解文件结构
